# Driver-selectable CAN vehicle profiles

Implementation plan for dashcam v0.4 • 28 November 2026

## 1. What the driver gets

The driver selects **Honda Brio DD1 CVT (2019)** or **Hyundai Tucson diesel (2022, Vietnam)** in ES3 Settings. The same selection is available headless on the Jetson. The Jetson records all observable frames from its own `can0`, decodes the selected vehicle’s verified signals in C++17, and supplies timestamped readings to the recording overlay. Both receivers share the vehicle OBD connector. The MKR remains connected for diagnostics and the C3 carries its telemetry, GNSS, IMU and switches. A missing camera, display, CAN wire or bridge can degrade its own functions independently.

A Brio drive can be replayed after a DBC correction because recording precedes profile filtering. The Tucson can have a usable diagnostic profile before its broadcast DBC is known. An OBD-II reply establishes diagnostic access for the PID and test setup involved. It does not establish which proprietary broadcasts reach the tap. Vehicle support is published per variant, tap and field.

**Owner decisions (28 Nov).** On the Vietnam Tucson the owner tested speed and RPM using the MKR CAN hardware itself. The driver must explicitly enable OBD-II in ES3 Settings once. Remember that preference for this Tucson profile and resume on later drives while it is selected. Retain the existing MKR ten-item polling cycle. Only verified diagnostic speed and RPM enter the Tucson v1 vehicle state. Keep the lower-level bridge trace available for engineering diagnostics. The Waveshare termination resistor is fitted; the two nodes will share the same OBD connector.

The deliverables are a passive SocketCAN receiver and archive, a versioned vehicle catalog, one decoder shared by live and replay, a field-by-field source selector, an MKR OBD-II mode controller, and ES3/headless selection. Implementation covers native acquisition and logging. The existing MKR raw-USB logger remains a reference instrument for the Brio comparison and historical captures. The former proposal to port its serial framing, device clock recovery and two-second disk hold is superseded.

## 2. Hardware baseline and vehicle evidence

| Item | Evidence and consequence |
|---|---|
| Jetson inspected on 28 Nov | SSH identified an Orin Nano Engineering Reference Developer Kit Super, L4T R36.5.2, kernel 5.15.199-tegra. The host sees `can0` on `c310000.mttcan`, MTU 16, controller clock 50 MHz. It was administratively DOWN/STOPPED, with zero RX/TX packets and error counters. This confirms driver binding. Actual traffic, bitrate, listen-only readback and physical pin routing still need a vehicle or bench source. |
| Capture clock | `ethtool -T can0` advertised software RX/system-clock timestamps, no PTP hardware clock and no hardware RX timestamp modes. Use kernel software RX time as the initial contract. A nanosecond representation describes resolution, not physical accuracy at the wire. |
| Deployed system | `candump` is installed. The v0.4 service was active and its container uses host networking. The SD card was mounted at `/mnt/sdcard`. No MKR, C3 or ES3 USB serial device appeared in this inventory. The probe only read existing state. |
| Waveshare interface | Owner reports the SN65HVD230 is soldered. TI specifies a 3.3 V transceiver rated up to 1 Mbit/s. Configure Classical CAN for this assembly. The published Waveshare schematic shows R2, 120 Ω across CANH/CANL. The owner confirms that the termination resistor is fitted. On an already terminated vehicle bus, isolate/remove the Waveshare termination before installing the parallel tap; verify the exact PCB revision and MKR shield termination too. The host’s listen-only flag cannot disconnect a resistor. [TI specifications](https://www.ti.com/product/SN65HVD230) · [Waveshare schematic](https://files.waveshare.com/upload/c/c5/SN65HVD230-CAN-Board-Schematic.pdf) |
| Brio | The repository documents 500 kbit/s F-CAN at OBD-II pins 6/14, 13 mapped signals on six standard IDs and the evidence for their meanings. This is the reference vehicle for simultaneous capture. [Measured Brio map](peripherals/mkr_zero/config/canmap.brio.txt) |
| Tucson | Owner verified speed and RPM with this MKR CAN on the Vietnam diesel. A matched local broadcast DBC and a passive capture have yet to be established. Upstream distinguishes its 2022 fourth-generation CAN FD entry from an older diesel platform. Record exact trim, connector, observed format/rates and trace evidence before enabling direct DBC bindings. A Classical diagnostic channel and an FD broadcast network can coexist on a vehicle. [Hyundai platform definitions](https://github.com/commaai/opendbc/blob/master/opendbc/car/hyundai/values.py) |

**Bring-up evidence to collect.** Check the soldered module against the specific carrier pinout (Orin Nano J17 pin 1 RX, pin 2 TX), supply, ground, CANH/CANL, connector branch and termination. On the isolated module with power removed, verify the fitted resistor and its isolation after the termination change. On a conventional two-terminated bus a third 120 Ω in parallel would change the nominal load from 60 Ω to 40 Ω; confirm the actual topology and check resistance only on a de-energized circuit. No rework was performed for this plan. Treat the vehicle’s already terminated bus as a tap. Confirm the pinmux survives reboot. On a documented Classical bus configure the Jetson host for the verified bitrate, explicitly set listen-only on, controller loopback off and FD off, then check actual netlink state before starting the reader. The shipped loopback program sends frames and continues after configuration failure, so use a passive collection tool for the vehicle test. [NVIDIA hardware guide](https://docs.nvidia.com/jetson/archives/r36.5/DeveloperGuide/HR/ControllerAreaNetworkCan.html) · [Repository test program](src/tests/can_test.cpp)

Example for the known Brio link during scheduled bring-up, after confirming the interface is available for configuration:

```sh
sudo ip link set dev can0 down &&
  sudo ip link set dev can0 type can bitrate 500000 listen-only on loopback off fd off &&
  sudo ip link set dev can0 up &&
  ip -details -statistics link show dev can0
# After verifying the readback, passively sample for up to ten seconds.
timeout 10s candump -L -n 100 can0
```

Check for `LISTEN-ONLY`, 500000 bit/s, Classical MTU and increasing RX counts. Record CAN error/interface counters before and after. A silent or stationary car can legitimately yield zero frames. On the Tucson, first establish the intended tap’s physical layer and nominal/data bitrate from documentation or an appropriate passive analyzer. If the useful traffic requires CAN FD with high-speed data, keep the diagnostic feature available and qualify an FD-rated transceiver or adapter before enabling that direct input. One Orin Nano controller samples one physical bus at a time.

## 3. Components, data flow and ownership

```text
Vehicle broadcast bus → Waveshare → Jetson MTTCAN / can0 (listen-only)
                                      ↓
                      can_capture (C++ service)
                       ├─ whole-bus archive + RX/loss/clock events
                       ├─ selected DBC → fresh per-signal CAN values
                       ├─ bridge observations → field selection → snapshot journal
                       └─ catalog, persistent selection, status and replay metadata
                                      ↕ local Unix socket
Vehicle diagnostic bus ↔ MKR CAN ↔ C3 → v0.4 CommLink → bridge observation feed
                           ↑              ↕
                    mode requests    v0.4 recorder, overlay, ES3 link and picker

Headless candb CLI → same service API        Archives + profile assets → C++ replay
```

| Owner | Responsibility and integration point |
|---|---|
| Host interface setup | Bring up and verify the approved `can0` bus mode once. Only this component administers the link. Keep profile decoding and bitrate administration distinct. On incompatible or unconfirmed hardware report a direct-input fault. Continue serving diagnostic/UI functions. |
| Native `can_capture` service | Own profile revisions, active generation, SocketCAN reader, archive, source selection and local IPC. Keep running when v0.4 restarts. In the absence of v0.4 the CAN archive continues and bridge observations expire. Use a bounded disk writer and a separate control/config path. |
| Existing v0.4 process | Keep the existing single C3 tty owner and its callbacks for time, GNSS navigation and bridge logging. Add a nonblocking bridge observation/control adapter. Pass fallback policy requests from the service to the existing C3 link, report actual mode and forward a bounded stream of bridge samples. Sample merged vehicle data on the existing 200 ms overlay tick. [Supervisor](src/dashcam_v0_4.cpp) · [Bridge API](lib/libcommlink/libcommlink.h) |
| ES3 display | Retain the sole display tty owner in v0.4, separate from the C3. Add the picker in ES3 firmware, announce capability and refresh current state from the Jetson after reconnect. The display holds transient UI state only. [Display link](lib/libes3display/libes3display.h) · [ES3 settings](peripherals/es3c28p/lib/es3Graphics/es3GraphicsSettings.cpp) |
| CLI and replay | Link the same C++ library as the service. Headless commands operate over local IPC. Replay accepts recorded packages, raw and bridge data offline without opening CAN, a bridge tty or a display. |

A recorder outage interrupts bridge ingestion in this split. Mark this interval in the archive and present CAN-only coverage until v0.4 reconnects. If independent OBD/GNSS logging through camera-process downtime later becomes a requirement, transfer the sole C3 tty owner to a persistent telemetry service and feed v0.4 from IPC. Avoid two readers competing for the same C3 device.

## 4. Direct SocketCAN ingestion

1. Extend [libcan](lib/libcan/libcan.cpp) with a timestamped receive API while preserving current callers of `setReceiveCallback`. Reuse [CanFrame](lib/libcan/libcan.h) for ID, standard/extended format, RTR, frame type, DLC and payload. Keep socket/interface errors and controller notifications out of the DBC decoder. Treat the host-configured interface as a prerequisite for acquisition only. Reopen with bounded backoff on link-down, device removal or socket failure. Keep video and diagnostics running during retries.
2. Replace the receive-only plain `read()` path with `recvmsg()` for kernel RX timestamps and `SO_RXQ_OVFL` ancillary counts. Preserve both kernel realtime and local monotonic observation. Track measured realtime/monotonic offsets by epoch so NTP/GNSS wall-clock steps cannot rejuvenate stale data. Mark clock discontinuities and missing ancillary data. Expose receive-buffer size actually obtained. Check truncation, frame length and standard/extended identity before interpreting payloads.
3. Fix `setFilters({})` before using it for capture. The public header promises pass-all, whereas Linux interprets a null zero-length filter list as receive-none. Implement explicit pass-all for data, verify errors and add a regression on `vcan`. Archive all observable frames under every profile, including raw-only. Resolve the active profile’s IDs in user space. If another socket uses exact filters, mask EFF and RTR as appropriate. [Linux receive filter contract](https://docs.kernel.org/networking/can.html#raw-socket-option-can-raw-filter)
4. Assign a stream-instance ID and increasing observation sequence on receipt. Enqueue bounded batches to the disk writer and decode path. Check capacities during burst replay. Record socket-drop counter deltas including wrap/reset, netdevice errors/overruns, application queue drops and archive-write failures **separately**. Some metrics overlap; report each at its measurement point. Mark unavailable statistics and gaps explicitly.
5. Poll or subscribe to link health and publish interface uptime, bitrate, observed frames/s, matched frames/s, last data time, queue high-water marks and loss deltas. Debounce logs. A socket that opened successfully, diagnostic traffic alone, or a single matching numeric ID cannot qualify a vehicle profile. A delayed frame may be archived while its live reading has already expired.
6. Keep one-time link setup on the host. The initial receiver can run in host networking or as a native host service with suitable libraries. Make C++ binaries/build targets independent of GStreamer/CUDA for host tests. Run the capture service separately from v0.4 and bind-mount only its IPC directory into the recorder as needed. Avoid taking `can0` down on every camera or profile restart. [Current build](Makefile) · [Recorder launcher](docker_dev/launchcode_v0_4.sh) · [Service definition](docker_dev/dashcam-v04.service)

## 5. Vehicle packages, normalization and decoding

Install one immutable revision per vehicle variant. Proposed layout is `config/vehicles/<id>/<revision>/profile.xml`, an optional self-contained DBC, provenance/validation notes and a short replay fixture. A diagnostic-only Tucson revision may omit the DBC. Use the repository’s pugixml dependency for manifest parsing. Pin a revision of **dbcppp** after a C++17 ARM64 build and bit-vector test. Record its exact upstream revision, dependencies and license. Record source, redistribution terms, revision and content hash for each DBC. Flatten upstream generator imports before packaging. [C++ DBC library](https://github.com/xR3b0rn/dbcppp)

| Manifest section | Fields and validation |
|---|---|
| Identity and inputs | Stable ID, human-readable year/model/powertrain/market, immutable revision, compatible capture format and bitrate, tap identifier, status of direct and diagnostic coverage. Reject duplicate revision identities with different contents. Separate a profile’s required bus parameters from the installed adapter capabilities. |
| Bindings | Canonical field, DBC message and signal, physical unit, permitted conversion, enum table, invalid raw values, optional valid/status bit and freshness window. Resolve at load time, validate length/DLC, signedness, both endian conventions, offset, multiplexor and extended flag. Reject unsupported constructs with message/signal names. |
| Semantics and calibration | Distinguish stalk from flashing lamp, brake switch from pedal position, selector from actual gear, EPS assist effort from driver torque or steering angle. Derived fields name their inputs, calibration and expiration. Wheelbase/yaw calibration belongs to its vehicle revision. |
| Diagnostic evidence | Per-PID support and observed units, test setup/date, expected responder, measured effective update interval, any observed invalid values and fallback priority. Track query capability separately from fields validated for presentation. |

**Brio conversion.** Start from the measured text map. Vehicle speed is ID `0x158`, Motorola start 7, length 16, scale 0.01 km/h. Cross-check engine RPM, pedal raw-to-display conversion and both brake fields on `0x17C`; selector enums on `0x191`; assist effort on `0x1AB`; rear/front wheels on `0x1D0`; stalk position on `0x294`. Assert all 13 rows and six IDs reproduce the legacy decoder at matched sample instants. Test the existing indicator hold and unknown hazard state. Preserve `yawscale` and its calibration conditions wherever derived yaw is enabled. Historical replay should distinguish uncalibrated yaw from GNSS-calibrated live estimates. [Brio source of truth](peripherals/mkr_zero/config/canmap.brio.txt) · [Legacy decoder](peripherals/mkr_zero/tools/canstream/can_decode.cpp) · [Vehicle semantics](peripherals/mkr_zero/lib/CANSniffFunctions.cpp)

**Tucson progression.** Carry forward the owner’s verified MKR speed and RPM, then record a reproducible trace of both through the new host path. Permit an OBD-capable profile with unsupported fields absent. For direct CAN, capture timestamped stationary observations of brake, selector and indicators, and a recorded drive with an independent speed reference. Correlate expected payload lengths, byte order, scales, units, cadence and transitions. Check unknown/status codes, direction, stopped/parked cases, ignition cycle and disappearance of a message. Promote only the verified fields to a new immutable package revision. Keep synthetic overlapping-ID/endian/mux fixtures labeled as software tests.

## 6. Tucson OBD-II fallback and source selection

**Two independent states drive this feature.** Selecting a vehicle chooses the DBC, bindings and source policy. Enabling diagnostics authorizes the MKR to send its existing Service 01 queries. Raw Jetson capture stays passive throughout. A Tucson selection with no prior opt-in performs no new diagnostic enable. A persisted Tucson opt-in resumes on later drives, even while the direct DBC is absent or individual broadcast signals are healthy. This keeps OBD readings ready for per-field fallback. An empty bus or a stale field never grants opt-in.

### Command flow and recovery

| Event | Durable intent and runtime action | What the driver sees |
|---|---|---|
| First Tucson selection | Create or read the stable vehicle identity’s preference; default off. Start passive observations if compatible. | Tucson selected; OBD-II off. GNSS speed may still be available. |
| Driver enables OBD-II in Settings | Save the Tucson opt-in atomically. Send a generation-tagged desired state to v0.4, which uses its existing `CommLink::setCanMode(3)` through the C3. Keep the existing MKR PID sequence. | Enabling → mode confirmed → speed/RPM receiving as each actually arrives. |
| Next drive or bridge reconnect | Reload selected identity and saved opt-in. Wait for a fresh C3/MKR session and actual mode, then reconcile once as appropriate. A compatible revision of the same vehicle identity can inherit the preference. | Enabled preference stays visible separately from bridge offline, waiting for ECU, or receiving data. |
| Driver disables, selects Brio, or chooses raw-only | Persist disable if explicitly requested. Switching vehicle retains the dormant Tucson preference. Target MKR `DISCOVER` (mode 1) and immediately invalidate diagnostic candidates. Observe the reported mode before saying physical polling has stopped. | Disabled, stopping, or bridge offline / mode unconfirmed. Returning to the opted-in Tucson resumes polling. |
| Jetson service or C3 link disappears | Expire affected fields, clear pending transactions and record the gap. A running MKR can remain in its last mode without the command link. On orderly shutdown request passive mode when possible. Reconcile from fresh state after recovery. | Report last confirmation time and current uncertainty; a stopped telemetry stream alone is insufficient proof that diagnostic requests stopped. |
| Command writes succeed but ECU never replies | Distinguish command delivery, MKR mode, valid PID samples and ECU timeout. Respect the firmware’s bounded retries and eventual return to DISCOVER. Latch a session failure after exhaustion; avoid immediately rearming the MKR on every status frame. Allow an explicit retry or a genuinely new drive/session. | “Enabled · no ECU response” with retry. Camera and passive capture continue. |

There is a single settings authority and one C3 command owner. Serialize profile switches and preference changes. Include request ID and profile generation, discard late decisions, and notify the UI only for its current token. For startup with the bridge absent, accept a persisted preference as intent and expose pending hardware confirmation. For a stale bridge after switching away, reject its samples even if it later delivers a buffered old reading. Check `canMode`, MKR uptime discontinuities, C3 connection epoch, host frame age and per-field validity. The present `setCanMode` confirms a local write only; the C3 can drop a downstream request when busy. Use bounded retry of a transition and observe fresh subsequent telemetry for completion. [Host command semantics](lib/libcommlink/libcommlink.h) · [C3 forwarding](peripherals/esp32-c3/src/main.cpp) · [MKR recovery](peripherals/mkr_zero/mkr_zero.ino)

**Poll cycle and visibility.** The existing MKR polls RPM, speed, coolant, fuel level, fuel rate, throttle, load, barometric pressure, gear ratio/gear and odometer. The Tucson profile allows **PID 0x0D speed (km/h)** and **PID 0x0C RPM (rev/min)** into normalized telemetry. Keep the existing request rate, per-PID expiry and no-reply backoff. No PID-mask firmware extension or raw-CAN-over-C3 protocol is required. The diagnostic exchange uses the existing MKR addressing and 500 kbit/s setup. Verify it against the known working installation. On the shared branch, Jetson may record the MKR’s requests and ECU replies. Label those frames as diagnostic traffic, exclude them from broadcast profile-health counts, and use the C3/MKR observations as the diagnostic source for live output. [MKR poller](peripherals/mkr_zero/lib/OBD2Functions.cpp) · [Addressing and timing](peripherals/mkr_zero/lib/OBD2Functions.h) · [Telemetry packing](peripherals/mkr_zero/lib/CommunicationFunctions.cpp)

### Field policy for live and replay

| Field | Selection in profile mode |
|---|---|
| Vehicle speed | Fresh verified DBC speed → fresh GNSS ground speed with valid fix → fresh verified MKR OBD speed → unavailable. Preserve the current speed precedence. If both GNSS and OBD are live on the Tucson, the overlay labels GNSS; the diagnostic status can still show the OBD reading and its availability. |
| Engine RPM | Fresh verified DBC RPM → fresh verified MKR OBD RPM for the opted-in Tucson → unavailable. RPM can switch source independently of speed. |
| Selector, brake, pedal, wheels, indicators, hazard, steering | Use each verified direct binding and its validity/age. Leave unverified fields unavailable. Treat a measured zero, brake released, or stalk centered as an observation. Keep numeric transmission gear distinct from selector position. |
| Position, course, GNSS speed, IMU, switches | Use bridge-specific freshness and validity. Suppress unrelated bridge-sniffed vehicle values in direct-profile mode. Preserve existing bridge behavior when the feature is disabled. |
| Derived acceleration/yaw | Label source and calibration, reset state on relevant source/generation changes and gaps, and require sufficient fresh input. The MKR speed-derived acceleration belongs to its observed speed source; never present it as derived from unrelated Jetson or GNSS speed. |

Each normalized field carries source enum, validity, value/unit, observation time, and age/age basis. C3 telemetry repeats MKR readings. Honor the firmware’s per-PID expiry to NaN, `sigSource`, fresh telemetry and OBD mode. Require mode and post-transition evidence in the current generation. The wire lacks exact ECU acquisition timestamps for each PID; label bridge observation time separately and do not infer a new ECU sample from every 10 Hz packet or from an unchanged numeric value. Apply existing GNSS fix freshness and invalidate all stale fields even when other fields continue updating. Produce the headline overlay, vehicle-detail view and normalized log from the same snapshot. Keep the original bridge engineering CSV identifiable as such. [Existing overlay policy](src/bridge_overlay.h) · [Host wire fields](lib/libcommlink/HostProtocol.h) · [Bridge CSV](src/telemetry_log.h)

## 7. Selection, recording and deterministic replay

- **Authority and storage.** Install read-only catalog packages and keep mutable selection/preferences in a small service-owned file on durable Jetson storage. Key OBD opt-in by stable vehicle ID. On first install default to raw-only (or a configured initial vehicle) and diagnostics off. Validate saved selection against the installed package. On corrupt/missing/unsupported data report the reason, continue raw acquisition on the approved bus configuration, and reconcile to passive MKR mode. Use a temporary file, flush, same-filesystem rename and directory sync for updates.
- **Activation boundary.** Parse and validate a candidate away from the RX thread. On activation commit an ordered event containing service instance, old/new generation, stable ID, revision, DBC/manifest hash, preference, time and first affected observation sequence. Include a monotonic event sequence even when no CAN frames arrive or only bridge data is present. Atomically swap immutable decoder state and clear old holds, caches and derived values. A failed candidate leaves the previous working selection in effect. On restart record a fresh initial generation before accepting observations; use a durable selection record plus recovery marker to resolve a crash between save and activation. Signal loss if a policy boundary cannot be recorded.
- **Raw archive.** Keep a candump-compatible `can_raw.log` for existing offline tooling. Preserve full payload, interface, standard/extended ID, RTR, timestamps and frame ordering. Add a versioned capture index or equivalent native event stream linking raw row/part and sequence to the monotonic epoch, generation and loss intervals. Keep controller errors separate from normal data. Record diagnostic frames just like other observed bus frames. Do not synthesize MKR-only `FS` or console statistics for a SocketCAN capture.
- **Reconstructing the overlay.** Journal the bridge observations used for source selection (including session identity, MKR uptime, freshness evidence, mode, GNSS, OBD flags and values), selection/opt-in confirmations, clock epochs, losses and periodic evaluation ticks. A raw CAN log alone cannot reproduce GNSS fallback or historical C3 visibility. Capture the normalized snapshot actually presented to v0.4, or an evaluation tick with its consumed snapshot sequence, and link the video segment and overlay sample to that record. Preserve missing samples explicitly. Group these files by capture instance; camera segments can rotate independently.
- **Disk behavior.** Give raw writes and metadata bounded queues, reserve space for gap/control events, batch writes and rate-limit flushes. A full or hung SD must not block the reader, recorder or UI. Report branch-specific drops on recovery. Choose separate retention limits and a named fallback directory following the recorder’s mounted-footage checks. Retain a profile revision and index at least as long as the referenced raw segment; never delete an open session. Following an unclean shutdown, recover complete records, mark truncated tails and start a fresh stream instance.
- **Offline CLI.** Implement `candb list`, `validate`, `status`, `select`, `replay SESSION` and an explicit `replay --profile ID@REV INPUT` override. Provide headless initial config and selection; preserve the owner’s requirement that the initial diagnostic grant comes from ES3 Settings. Replay uses the recorded profile and policy by default. Archive exact redistributable packages by hash or require an exact externally retained copy. A retrospective override labels its provenance. Old MKR candump files can be decoded with explicit profile; expose only the channels supportable from their inputs.

## 8. UI and process integration

1. Add a `Vehicle CAN` config section to [libconfig](lib/libconfig/libconfig.h) and the [sample config](config/dashcam.xml). Include enable, interface, approved transport/bitrate, catalog root, state path, IPC location, capture output/limits, and optional first-install profile. Validate dimensions and deadlines at startup. Start recorder and headless selection even if the interface is down or the display is absent.
2. Use a versioned local Unix socket, for example `/run/dashcam-can/service.sock`. Give the systemd service its runtime directory and persistent state. Validate local peer permissions, request length, supported schema and catalog IDs. Define catalog/list, selection, diagnostic intent, observed mode, bridge observation, current snapshot and status messages. Bound queues, coalesce superseded UI snapshots, and count bridge-journal gaps separately. Resynchronize catalog and current generation after reconnect. Saving a preference can succeed while activation is pending. Return those outcomes independently.
3. Update the current [recorder callback/tick path](src/dashcam_v0_4.cpp). Register the bridge observation callback whenever vehicle profiles are enabled, including configurations with GPS time, navigation and bridge CSV all disabled. Retain a single `CommLink` instance. Use a worker to exchange IPC and commands so bridge callbacks and camera paths do bounded work. Record field age and actual sample identity; an overlay redraw never restamps an old observation as freshly received.
4. Implement a paginated vehicle picker and Tucson-only diagnostic toggle in [ES3 Settings](peripherals/es3c28p/lib/es3Graphics/es3GraphicsSettings.cpp). Show active variant and separate states for direct reception, matched/verified signals, OBD enabled preference, actual MKR mode, ECU data, and offline/stale conditions. An actionable example is “Tucson · OBD enabled · RPM via OBD · speed via GNSS”. Unavailable and measured zero render differently.
5. Extend [ES3 control framing](peripherals/es3c28p/lib/es3UsbLink/Es3Protocol.h) and the [host display client](lib/libes3display/libes3display.h) using a negotiated capability, bounded catalog pages, polled pending action/token and applied-result response. Reserve command numbers against video/map/pan, fit the existing 128-byte payload, synchronize firmware/host header copies and shared golden vectors. Use stable IDs through reconnect and ignore duplicate taps. Start the display link in controls-only mode when preview and map are both disabled. An older display leaves headless vehicle selection available.
6. Distinguish the engineering view from the supported vehicle view. The former can report raw bridge fields and socket counters; the normalized Tucson view advertises only speed and RPM from OBD. Tag each public value with its actual source. No Android/cloud picker or remote diagnostic enable is part of this release.

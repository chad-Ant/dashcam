# Remote monitoring implementation plan

**Status.** Proposed design for dashcam v0.4. Start here, then follow either mode plan. Both modes ship in the same Jetson service, Android app, web dashboard, and relay deployment.

| Owner setting | Idle behavior while the vehicle has power and internet | First connection | Cloud cost driver |
|---|---|---|---|
| [On demand](CLOUD_ON_DEMAND_PLAN.md) | The Jetson listens to its own Firestore control document. | Viewer demand wakes the uplink. A cold relay and a new device connection may add latency. | Live relay time, Firestore operations, and viewer traffic |
| [Ready while powered](CLOUD_READY_WHILE_POWERED_PLAN.md) | The Jetson maintains an authenticated control socket to Cloud Run. | An online, ready device receives the request over the open socket. | Relay time while at least one device is connected, and viewer traffic |

Design for two enrolled Jetsons, five simultaneous viewer sessions in total, and one selected vehicle per session. A single viewer can use telemetry and camera together. Use **On demand** as the proposed default for a newly enrolled vehicle because free or near-free operation is a priority. The owner can pick the other default at enrollment. Existing LAN-only installations acquire no cloud behavior until enrolled.

## User experience and prerequisites

| Who or what | Needed for the pilot |
|---|---|
| Cloud owner | A billing-enabled Google Cloud project, access to deploy Cloud Run and a container image, configure Firestore and Firebase Authentication, assign runtime identities, and view billing/metrics. Use a controlled deployment identity and an owner email for billing alerts. Configure alerts before the real-vehicle trial. |
| Region and address | Choose a Cloud Run region convenient to the vehicles and viewers and a nearby supported Firestore location before creating the database. The default HTTPS `run.app` address suffices. Test LTE latency and price in the actual region. |
| Users | First owner identity, up to five invited test users or sessions, and a record of which users may view or administer each Jetson. Use a stable authentication UID for permissions. |
| Vehicles | Shell access to provision each Jetson once, its existing connector identity and trusted local TLS configuration, working local telemetry, power, correct time and outbound DNS/HTTPS. Enable the existing monitoring preview for video. A cellular router behind NAT is suitable. |
| Clients | A browser on an external network, an Android phone with cellular data, and an Android build environment compatible with the repository's Gradle wrapper and SDK. Use a test APK with its own registered sign-in configuration. |
| Field validation | Access to both Jetsons, permission to simulate connectivity loss while parked, and a way to check footage and frame counters afterwards. Decide what monthly spend and typical viewer-hours are acceptable. |

Both clients present **Connection → Cloud → vehicle → Connection mode** to the owner. Show the two labels above with a short explanation of responsiveness and billable uptime. A viewer can connect, leave, and request camera preview. Only an owner can change policy. Distinguish **Last seen**, **Connecting**, **Live**, and **Offline**. A one-minute heartbeat is evidence of device presence. Only fresh samples make telemetry or video live. A mode change is independent of the local/cloud selection and camera button.

## Shared implementation work

1. **Keep the existing local data path.** The C++ recorder publishes to Unix sockets already owned by the Python connector. Add a separate host systemd service for the cloud uplink. Have it subscribe as one authenticated local client to `/v1/stream` only during telemetry demand and to `/v1/video` only during camera demand. Provision local endpoint trust using the existing certificate or pin. Keep its local credential on the host. The uplink needs outbound networking; the current LAN service has a systemd IP allowlist. Avoid a second reader binding the recorder's datagram sockets. [Connector protocol](README.md) · [LAN service unit](dashcam-monitor.service)
2. **Enroll the vehicle.** An owner creates a single-use, short-lived enrollment code. The uplink exchanges it over TLS and receives a revocable device identity bound to the Jetson ID. Store device secrets in a restricted service-owned file. Make enrollment retry-safe if the reply is lost. Provide rotation and revocation commands. Keep a distinction between the cloud credential, user sign-in and existing LAN pairing. Revoking the cloud device closes its relay session.
3. **Use a private control document per device.** Store the desired mode, monotonic configuration version, current requested channels, demand generation and expiry. Keep device-reported presence and applied configuration version in a separate document so heartbeats do not trigger demand notifications. Keep viewer grants and leases in server-controlled records. Store no GPS samples, images or raw pairing links in these records or logs. Grant each device read access to its own configuration and permission to report its own status. The relay writes demand and settings after authorization. A Firebase-authenticated client or suitably scoped gateway must enforce this boundary; server SDKs use IAM and bypass Firestore Security Rules. Test the chosen Jetson listener and token refresh on the actual ARM64 host before integrating media. [Firestore authorization](https://firebase.google.com/docs/firestore/security/rules-conditions)
4. **Implement the relay.** Start with one Cloud Run service, request-based billing, minimum zero, a pilot maximum of one instance and concurrency sufficient for both device sockets and all viewer channels. Serve the web client and API from the same HTTPS origin. Suggested routes include `GET /vehicles`, `PATCH /vehicles/{id}/connection-mode`, viewer telemetry/video upgrades scoped to a vehicle, and a separate device upgrade. Keep live frames in memory. On deploy, drain sockets and reconnect both ends to a single serving revision. Cloud Run instance limits and affinity alone do not guarantee co-location across revisions or replacements. Identify the current relay owner for each device with a server-issued session generation, reject obsolete sockets, and exercise revision changes in staging. Multiple concurrently serving replicas would require shared routing or a broker before rollout. [Cloud Run WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets)
5. **Authenticate clients at the public boundary.** Use authenticated, invited Firebase users. On web, exchange verified sign-in for a secure HttpOnly session cookie, check request origin for cookie-authenticated upgrades and protect settings writes from cross-site requests. On Android, verify the user's short-lived token on the server. Authorize the device ID on every subscription and mode change. Expire or revoke already-open sockets and stop associated demand; a handshake alone cannot enforce expiry. Bind incoming Jetson data to the authenticated device and active session. Never use a client-supplied ID alone to select another vehicle's feed.
6. **Reuse both dashboards.** Add a cloud transport and an authenticated vehicle picker without duplicating camera, map or telemetry cards. Preserve existing local profiles on Android. The remote transport uses the default network and public TLS trust; the LAN transport already binds sockets and DNS to Wi-Fi and pins the Jetson certificate. Scope Android's local-network permission prompt to LAN operations. Browser navigation and Android lifecycle changes must release subscriptions. Start video on explicit camera demand, and release it on app background, page hide or vehicle switch. [Web client](web/app.js) · [Android transport](../android/app/src/main/java/com/dashcam/connector/MonitorRepository.kt) · [Activity lifecycle](../android/app/src/main/java/com/dashcam/connector/MainActivity.kt)
7. **Use bounded subscriptions.** Aggregate authenticated viewers per vehicle and channel. On the first viewer, issue demand; on the last, release it. The existing Jetson agent allows four local viewers per channel. One shared upstream can supply five remote clients while consuming one local slot. Surface local capacity errors if other LAN viewers occupy all slots. Keep the existing JSON snapshot and binary DCV1 JPEG format for viewers; carry control messages on the device connection only. Use bounded per-viewer output, drop superseded samples and prioritize control/telemetry over video. Disconnect a persistently slow viewer. Protect local recording from network backpressure.

## Proposed interfaces and ownership

These names describe new cloud endpoints. Local clients continue to use the connector routes documented in the [protocol reference](README.md).

| Interface | Caller and contract |
|---|---|
| `GET /v1/vehicles` | Signed-in client. Return only granted vehicles, role, capabilities, last seen, desired mode, applied mode and configuration version. Use short HTTP requests for the vehicle list, including when all vehicles are offline. |
| `PATCH /v1/vehicles/{id}/connection-mode` | Owner. Body carries the mode and expected version. Return the committed desired version and last device acknowledgement. Return a conflict for an obsolete expected version and the same result for an idempotent retry. |
| `/v1/vehicles/{id}/stream` and `/video` | Authenticated viewer WebSockets. Use the connector's existing snapshot JSON and DCV1 binary payloads. Count the two sockets as one viewer session for the five-session limit. On an offline vehicle, end the pending upgrade or socket within the configured deadline. |
| `/v1/uplink` | Enrolled Jetson WebSocket. The relay binds the authenticated principal to the allowed vehicle. Registration returns a new session generation. Device notifications include registration, heartbeat, applied configuration, telemetry and video. Relay commands cover requested channels, remaining lease time, policy changes and orderly closure. Use a small typed envelope for control/telemetry and a bounded binary message for each JPEG. |

Suggested Firestore schema:

| Path | Contents and writer |
|---|---|
| `vehicles/{id}/control/current` | Desired mode and version, demand generation, desired channels and lease expiry. Relay writes. The matching device may read. |
| `vehicles/{id}/status/current` | Applied mode and version, last contact, active session generation and capabilities. Accept only device-owned status fields from its authenticated identity. Relay owns the registration generation; use separate field permissions or a separate server-owned record. |
| `vehicles/{id}/members/{uid}` | Owner or viewer role. Restricted server writes. Invitations and removals update grants; they never convey device credentials to a user. |
| `vehicles/{id}/sessions/{sessionId}` | Viewer UID, requested channels, expiry and relay generation. Server writes. Derive demand from unexpired authorized sessions; use expiry checks in code even if database cleanup is delayed. |

Choose one serial writer or Firestore transaction per vehicle for demand changes. For example, if the last viewer on phone A leaves at the same time browser B starts, recompute the aggregate using both committed session changes. A late stop from A must not cancel B. A returning phone with an expired session obtains a new lease. Make retries of the same subscribe, release and mode update safe. Do not write every telemetry sample, video frame or WebSocket heartbeat to every viewer record.

## Toggle contract

| Concern | Proposed behavior |
|---|---|
| Source of truth | A durable policy per Jetson with `desiredMode` (`on_demand` or `ready_while_powered`) and `configVersion`. The device reports `appliedMode` and `appliedVersion`. These settings survive relay scale-down, Jetson reboot and app reinstall. |
| Owner writes | Include the last observed version and apply an atomic compare-and-set. Repeating a successful request for the same mode is idempotent. On conflicting changes from web and Android, refresh and display the winning version. Show **Pending** until the device acknowledges. |
| Device offline | Accept and persist the change. Show last seen and **Applies when online**. On startup or reconnect, read the latest server-confirmed policy before deciding to listen or connect. A locally cached mode can inform the UI; it cannot authorize a stream. |
| On demand → Ready while powered | Deliver the versioned change over the Firestore listener. Open or reuse the authenticated relay socket, register, then acknowledge. Once registration succeeds, retire the idle listener. If registration fails, keep the listener and retry with backoff. |
| Ready while powered → On demand | Send the versioned change on the open control socket. Establish the Firestore listener and reconcile its first current snapshot before acknowledging. If viewers remain, keep their uplink until the final subscription ends. With no viewers, close the control socket after handoff. |
| Lost acknowledgement or simultaneous events | Reconcile desired settings, live viewer demand and applied version after every reconnect. Ignore older configuration and demand generations. Only the current device session may send frames, clear demand or mark itself offline. Maintain at most one local telemetry reader and one local camera reader through handoff. |
| Owner change during a viewing session | Reuse the healthy data connection; the new policy determines what happens after viewing ends. If reconnection is necessary, show **Reconnecting** and expire the old picture. No command in either mode controls the recorder. |

**Timing defaults for measurement.** Use a 60-second heartbeat and mark a silently disconnected device offline after 150 seconds without valid traffic. An explicit close updates presence sooner. While viewers are active, renew a short demand lease, initially every 10 seconds with a 30-second lifetime. A Jetson uses a local monotonic deadline after receiving a valid lease. On receipt, account for its remaining server-side lifetime; receiving an expired or replayed command cannot start a fresh lease. This bounds unwanted upload after relay loss independently of the presence timeout. Preserve the existing two-second client display freshness check. Use finite reconnect backoff with jitter and reset it after a stable connection.

## Delivery order and release gates

1. Build the relay, common state machine, enrollment, and two simulated Jetsons. Exercise both mode transitions and stale-generation handling before adding media. Run against isolated local/emulated services where possible.
2. Deploy staging. Prove each mode separately with one Jetson and an authenticated browser. Capture control timestamps and time to first fresh telemetry and first decoded frame on real LTE. Progress from telemetry to video.
3. Add the owner toggle and readiness indicators to both clients. Perform the tests in each mode plan and the mixed-mode tests below. Estimate monthly charges from observed regional usage. [Cloud Run pricing](https://cloud.google.com/run/pricing) · [Firestore pricing](https://firebase.google.com/docs/firestore/pricing)
4. Enroll the second vehicle. Roll out to the five invited viewers after the shared acceptance checks pass. For rollback, stop the cloud uplink, revoke its cloud credential if appropriate, and revert the remote deployment. Verify the LAN dashboard and on-disk recording locally.

| Shared acceptance test | Evidence to capture |
|---|---|
| Mixed modes and load | Configure A on demand and B ready. Put all five viewers on A, then move two to B. Record exactly one upstream per requested channel per vehicle. Confirm no cross-vehicle frames or map fixes. |
| Atomic switching | Toggle both ways during recording, with and without viewers. Repeat a write, deliver updates out of order, race two owners, unplug the device before acknowledgement and reboot it. Check final desired/applied versions and active reader counts. |
| Access control | Use an owner, a viewer and an unassigned account. Verify per-vehicle discovery, settings writes, upgrades, token expiry and revocation on active streams. Try each device identity against the other device's control document. |
| Data and recorder isolation | Measure ten idle minutes in each mode. Only control/presence bytes may leave the vehicle. Check recording frame counters and saved footage through LTE loss, cloud restart and Jetson uplink restart. |
| Recovery and scaling | Exercise silent TCP loss, app backgrounding, device power loss, relay deployment, restart, expired demand, and a Cloud Run WebSocket timeout. Confirm the last viewer releases video and reconnect never replays old data. With both devices offline, background clients must not keep relay sockets open indefinitely. |
| Latency and cost | Target p95 tap-to-first-fresh-telemetry within 3 seconds for an online, reachable Jetson. Measure each mode separately over at least 100 attempts, including cold relay starts in the on-demand sample. Report first-frame latency independently. Record active instance hours, Firestore reads/writes and outgoing GiB. Billing outcomes depend on usage and region. |
